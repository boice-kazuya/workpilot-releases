# 動画構成分析アプリ（仮称: WorkPilot Video Lab）設計書

> 目的: 大量の動画を取り込み、「どう編集されているか」を機械的に分解・蓄積し、
> そこから編集技術を **AIスキル（SKILL.md）として育てる**。
> 最初は専用の分析アプリとして作り、後に WorkPilot の映像アドオンとして組み込む。

---

## 0. 結論（設計の骨子）

| 決めごと | 採用 | 理由 |
|---|---|---|
| 全体構造 | **エンジン先行（Engine-first）** | UI は薄く、分析エンジンを独立プロセス＋安定API にする。アドオン化は「包み替え」で済む |
| 実行場所 | **ローカル完結（Mac / Apple Silicon）** | WorkPilot と同じ思想。動画も特徴量も Mac から出さない |
| 技術スタック | **Electron + Vue 3 / Node エンジン + ffmpeg + Swift ヘルパー** | WorkPilot 本体の実装（§13 で確認済み）に揃える。Python を DMG に同梱しない |
| AIの使い方 | **信号分析（決定的）と意味分析（LLM/VLM）を分離** | 高価な LLM はキーフレームと要約にだけ使う。サブスク枠を溶かさない |
| 中心データ | **統一タイムライン（Analysis Bundle）** | すべての分析器が「時刻付きイベント」を同じ形式で出す。ここが資産 |
| スキルの形 | **SKILL.md（人間可読）＋ recipe.json（機械可読）のペア** | WorkPilot / Claude Code にそのまま取り込める |
| 育て方 | **蓄積 → パターン抽出 → LLM蒸留 → 人の承認 → 評価** | 勝手に書き換えない。評価で「効いたか」を数値で見る |
| 使い方（WorkPilot側） | **素材＋テーマ → スキル合成 → 構成案 → 組み立て → 自己評価** | スマホ動画を上げて一言頼むだけで BGM/SFX 入りの完成品が出る（§9A） |
| 学習元 | **ローカル動画＋YouTube（チャンネル単位のお手本）** | 動画本体は持たず、ルールだけを蓄積する（§9B） |

## 1. 何を分析するのか（分析の語彙）

まず「編集技術」を機械が扱える単位に分解する。これが分析器の仕様であり、スキルの語彙になる。

### 1.1 映像トラック

| カテゴリ | 検出項目 | 主な手法 |
|---|---|---|
| ショット境界 | ハードカット、ディゾルブ、フェードイン/アウト、ワイプ | PySceneDetect（Content/Adaptive）＋ TransNetV2、輝度カーブ |
| ショット種別 | クローズアップ / ミディアム / ワイド、人物/物/風景/テロップ画面 | 顔検出のサイズ比、CLIP/SigLIP のゼロショット分類 |
| カメラワーク | 固定、パン、ティルト、ズーム、手持ちブレ | Optical Flow（OpenCV） |
| エフェクト | スピードランプ、デジタルズーム（パンチイン）、フラッシュフレーム、シェイク、色調の切替 | フレーム時間差解析、スケール推定、輝度スパイク、色ヒストグラム距離 |
| グラフィック | テロップ、ローワーサード、タイトルカード、字幕、PinP、分割画面 | OCR（Apple Vision が速くて無料）、テキスト領域の位置と滞在時間 |
| ジャンプカット | 同一シーン内の不連続（Vlog・インタビューで頻出） | 連続ショットの類似度が高く、かつ話者が同じ |

### 1.2 音声トラック

| カテゴリ | 検出項目 | 主な手法 |
|---|---|---|
| 発話 | 区間、話者交代、文字起こし（単語タイムスタンプ付き） | whisper（mlx-whisper / whisper.cpp）、VAD、話者分離 |
| 音楽（BGM） | 入り・切れ・曲の切替、テンポ、ビート格子 | 音響イベント分類（PANNs/YAMNet/CLAP）、librosa のビート追跡 |
| 効果音（SFX） | ヒット、ウーッシュ、ライザー、ポップ等の瞬間イベント | オンセット検出＋AudioSet 分類 |
| ラウドネス | 区間ごとの LUFS、ダッキング（BGM が声の下で下がる） | ffmpeg ebur128、発話区間と BGM 音量の相関 |
| 無音 | 間（ま）、ブレス、不自然な空白 | 閾値＋継続時間 |

### 1.3 映像×音声の関係（ここが「編集技術」の核心）

- **J-cut / L-cut**: 音が映像より先行/後行してカットされているか（カット時刻と発話境界のずれ）
- **カット・オン・ビート**: カット点がビート格子にどれだけ乗っているか（許容 ±80ms で一致率）
- **BGM の入り方**: 発話/タイトル/ショット境界に対してどのタイミング・どの音量で入るか
- **SFX とエフェクトの同期**: ウーッシュとズーム、ヒットとテロップ出現の時間差
- **テロップと発話の同期**: 発話語とテロップ表示の遅延

### 1.4 構造（マクロ）

- **セグメント**: フック（冒頭0–5s）／タイトル／本編チャプター／CTA／アウトロ
- **チャプター境界**: 文字起こしの話題転換 × 映像の大きな切替 × BGM 切替 の重なり
- **リズム指標**: 平均ショット長（ASL）、カット密度の時系列、ショット長の分布、冒頭30秒のカット数
- **ジャンル指紋**: 上記の数値をまとめた特徴ベクトル → クラスタリングで「スタイル」を発見

## 2. アーキテクチャ

```
┌─────────────────────────── 専用アプリ（Mac） ───────────────────────────┐
│                                                                        │
│   UI（Vue 3 + Vite、WorkPilot と同じ）                                  │
│   ┌──────────┐ ┌───────────────┐ ┌────────────┐ ┌─────────────────┐   │
│   │ 取り込み  │ │ タイムライン   │ │ コーパス    │ │ スキル工房       │   │
│   │ キュー    │ │ ビューア      │ │ 比較/検索   │ │ (提案→承認→評価) │   │
│   └────┬─────┘ └──────┬────────┘ └─────┬──────┘ └───────┬─────────┘   │
│        └───────────────┴─── localhost HTTP/WebSocket ───┴─────────────┘│
│                                     │                                  │
│   Engine（Node/TypeScript、CLI でも単独実行可。重い処理は外部プロセス） │
│   ┌──────────────────────────────────────────────────────────────┐    │
│   │ Job Queue → Ingest → Probe → Extract → Analyzers(並列) → Fuse │    │
│   │                                      │                        │    │
│   │        信号分析（決定的・ローカル）      意味分析（LLM/VLM・承認制） │    │
│   │        ffmpeg filters / Swift helpers   Claude / GPT / Gemini   │    │
│   │        (Vision, SoundAnalysis, Speech)  (サブスク CLI 経由)      │    │
│   └──────────────────────────────────────────────────────────────┘    │
│                                     │                                  │
│   Store                                                                │
│   ┌──────────────┐ ┌─────────────────┐ ┌──────────────┐ ┌──────────┐  │
│   │ SQLite(索引) │ │ bundles/*.json  │ │ ベクトル索引  │ │ skills/  │  │
│   │              │ │ (統一タイムライン)│ │ (LanceDB)    │ │ SKILL.md │  │
│   └──────────────┘ └─────────────────┘ └──────────────┘ └──────────┘  │
└────────────────────────────────────────────────────────────────────────┘
```

### 2.1 Engine-first（最重要の方針）

- Engine は **UI を知らない**。`videolab analyze <file>` のように CLI 単体でも動く。
- Engine 本体は Node/TypeScript。重い処理は **外部プロセス**（ffmpeg、Swift ヘルパー、任意で Python スクリプト）に出し、JSON を stdout で受け取る。WorkPilot の `apple-stt` ヘルパーと同じ流儀。
- UI は Engine の HTTP/WebSocket API だけを叩く。
- WorkPilot アドオン化のとき、UI を WorkPilot のパネルに置き換え、Engine はそのまま同梱する。
- Engine の公開面は3つだけに絞る: **API**（ジョブ投入/進捗/取得）、**ファイル形式**（Bundle / SKILL.md / OKF / OTIO）、**イベント**（進捗・完了・承認要求）。

### 2.2 パイプライン（1本の動画に対して）

```
Ingest   : ファイル登録、コンテンツハッシュ(sha256)で重複排除、出所メタ記録
Probe    : ffprobe（長さ、fps、解像度、音声ch、可変fps か）
Extract  : 分析用プロキシ生成（360p/24fps, videotoolbox で高速）
           音声 wav(16k mono) 抽出、ショット境界ごとのキーフレーム、サムネ帯
Analyze  : 分析器を並列実行。各分析器は「トラック上のイベント列」を返す
Fuse     : 全トラックを1本の Analysis Bundle に統合、派生指標(§1.3/1.4)を計算
Index    : SQLite に要約値、LanceDB にショット埋め込みを登録
```

**分析器のインターフェース（統一）**

```ts
interface Analyzer {
  name: string            // "shots", "music", "ocr", ...
  version: string         // 変えると再実行対象になる
  requires: string[]      // 依存する先行分析（"shots" など）
  cost: "local" | "llm"   // LLM を使うものは承認制・後回し
  platforms?: ("darwin" | "linux")[]  // Swift ヘルパー依存のものは darwin のみ
  run(ctx: Context): Promise<Event[]>
}
```

- **キャッシュ鍵 = (コンテンツハッシュ, 分析器名, 分析器バージョン)**。
  分析器を1つ改良しても、他の結果は再利用される。大量取り込みの前提。
- **再開可能**: ジョブは分析器単位で完了を記録。途中でアプリを閉じても続きから。
- **信号分析は常に先に完走させ、LLM 分析は別キューで後から**。LLM なしでも Bundle は成立する。

### 2.3 LLM/VLM の使いどころ（枠を守る）

| 用途 | 入力 | 粒度 |
|---|---|---|
| ショットの意味タグ付け | キーフレーム数枚＋前後の文字起こし | ショット単位（上限あり） |
| チャプター命名・意図推定 | 文字起こし要約＋構造指標 | 動画単位 |
| 「なぜこの編集か」の仮説生成 | 派生指標のテキスト化（JSON→自然文） | パターン単位 |
| スキル蒸留 | 複数動画のパターン集計 | ジャンル単位 |

原則: **フレームを大量に LLM へ送らない**。送るのはキーフレームと数値要約。
WorkPilot 同様、外部へ出る前に「何枚・何文字送るか」を見せて承認を取る。

## 3. データモデル（統一タイムライン = Analysis Bundle）

1本の動画につき1つの JSON（＋サムネ等の付随ファイル）。すべての分析器がこの形に書く。

```jsonc
{
  "schema": "videolab.bundle/1",
  "video": {
    "id": "sha256:…", "path": "…", "duration": 312.4, "fps": 29.97,
    "source": { "kind": "upload", "genre_hint": "news" }
  },
  "tracks": {
    "shots":      [ { "t0": 0.00, "t1": 2.53, "type": "closeup", "camera": "static",
                      "transition_in": "cut", "embedding_id": "…" } ],
    "transitions":[ { "t": 2.53, "kind": "cut" }, { "t": 41.2, "kind": "dissolve", "dur": 0.6 } ],
    "effects":    [ { "t0": 12.0, "t1": 12.4, "kind": "punch_in", "scale": 1.15 } ],
    "graphics":   [ { "t0": 0.5, "t1": 4.0, "kind": "lower_third", "text": "…", "bbox": [..] } ],
    "speech":     [ { "t0": 1.2, "t1": 6.8, "speaker": "S1", "words": [ … ] } ],
    "music":      [ { "t0": 0.0, "t1": 58.0, "bpm": 96, "beats": [ … ], "lufs": -22.1 } ],
    "sfx":        [ { "t": 12.02, "kind": "whoosh", "conf": 0.91 } ],
    "loudness":   [ { "t": 0.0, "lufs_s": -18.3 }, … ],
    "semantic":   [ { "t0": 0.0, "t1": 2.53, "tags": ["anchor", "studio"], "by": "llm:…" } ]
  },
  "derived": {
    "asl": 3.1, "cut_density": [ … ], "cut_on_beat_ratio": 0.62,
    "jl_cuts": [ { "t": 41.2, "kind": "J", "lead_ms": 420 } ],
    "music_entries": [ { "t": 0.0, "relative_to": "video_start", "ramp_ms": 800 } ],
    "ducking": [ { "t0": 1.2, "t1": 6.8, "delta_db": -11.5 } ],
    "segments": [ { "t0": 0, "t1": 5.0, "role": "hook" }, … ],
    "fingerprint": [ 0.12, 0.88, … ]
  },
  "provenance": { "analyzers": { "shots": "1.3.0", "music": "0.9.2" }, "created_at": "…" }
}
```

設計上のポイント

- **トラック＝イベント列**。区間イベント（t0,t1）と点イベント（t）の2種類だけ。UI も検索も同じ扱いにできる。
- **derived は再計算可能**。tracks が真実で、derived は派生。式を変えたら全動画で再計算すればよい。
- **provenance** に分析器バージョンを残す。後で「古い分析器の結果だけ再実行」ができる。
- 外部連携用に **OpenTimelineIO（OTIO）へ書き出し**可能にする。WorkPilot のタイムライン編集や他の NLE に渡せる業界標準。

### 3.1 保存場所（WorkPilot 互換）

```
<ワークスペース>/
  videos/            取り込み元へのリンク or コピー（任意）
  cache/<hash>/      proxy.mp4, audio.wav, keyframes/, thumbs.jpg
  bundles/<hash>.json
  index.sqlite       動画一覧、要約指標、ジョブ状態
  vectors/           LanceDB（ショット埋め込み：類似ショット検索用）
  knowledge/         OKF/Markdown（Obsidian 保管庫に置ける。人が読む分析レポート）
  skills/<genre>/<pattern>/SKILL.md + recipe.json + evidence.json
```

knowledge/ と skills/ は **ただのファイル**。WorkPilot の「Obsidian 保管庫」「スキル取り込み」にそのまま乗る。

## 4. スキルを「育てる」ループ

```
 ①蓄積           ②パターン抽出          ③蒸留(LLM)         ④承認            ⑤評価
 Bundle 多数 ──▶ ジャンル別に集計 ──▶ SKILL.md 草案 ──▶ 人が差分を確認 ──▶ 保留動画で検証
                 クラスタリング          (根拠付き)        採用/修正/却下       スコア記録
      ▲                                                                       │
      └──────────────────── 新しい動画が増えるたびに ②から再実行 ◀─────────────┘
```

### 4.1 パターン抽出（決定的・LLM 不要）

- ジャンル（またはユーザーが付けたタグ）ごとに derived を集計し、分布として持つ。
  例: ニュースの ASL 中央値 2.8s、冒頭5秒のテロップ出現率 92%、BGM 入りは「発話開始の 0.3s 前」が最頻。
- ショット埋め込みをクラスタリングし、「よく使われるショットの型」を発見。
- 統計的に偏りが強い項目を「パターン候補」として並べる（効果量が大きい順）。

### 4.2 蒸留（LLM）

LLM には **集計結果と代表例（動画ID＋タイムコード）** を渡し、以下の形式で書かせる。

```markdown
---
name: news-cold-open
genre: news
version: 0.3.0
evidence: evidence.json      # 根拠となる動画IDと時刻の一覧
metrics: { cut_f1: 0.71, music_entry_mae_ms: 340 }   # §4.4 の評価結果
---
# ニュースのコールドオープン

## いつ使うか
報道・解説系。冒頭で結論を言い切るタイプ。

## ルール（数値付き）
- 0–3s: 見出しテロップを画面下 1/3 に出す（出現率 92%）
- 本編の B-roll は 2–4s で切る（ASL 2.8s、IQR 2.1–3.6）
- BGM は発話開始の 0.2–0.5s 前にフェードイン（800ms）、発話中は −10〜−12 dB にダッキング
- ナレーション境界では J-cut を優先（音を 300–500ms 先行）

## やってはいけないこと
- 冒頭 5s 以内のディゾルブ（出現率 3%。テンポを殺す）

## 根拠
- video:ab12… 00:00–00:05 / video:cd34… 00:00–00:04 …
```

同時に **recipe.json**（編集エンジンが解釈できるルール）を書かせる。

```jsonc
{ "rules": [
  { "when": "segment.role == 'hook'", "do": "overlay.lower_third", "at": "0.0-3.0" },
  { "when": "segment.role == 'body' && shot.kind == 'broll'", "constrain": "shot.len", "range": [2.0, 4.0] },
  { "when": "speech.start", "do": "music.fade_in", "offset_ms": -300, "ramp_ms": 800 },
  { "when": "speech.active", "do": "music.duck", "delta_db": -11 }
] }
```

人が読む SKILL.md と、機械が実行する recipe.json を **常にペアで**持つ。
片方だけが更新されるのを防ぐため、生成は必ず同じジョブで行い、評価は recipe.json 側で回す。

### 4.3 承認（WorkPilot の流儀に合わせる）

- 蒸留結果は **常に「提案」**。既存スキルとの差分（diff）を見せ、採用／修正／却下を人が決める。
- 却下理由は記録し、次回の蒸留プロンプトに「過去に却下されたルール」として渡す。
- 既存の WorkPilot と同じく「一時的に外す」「最終使用日」「A/B テスト」をメタデータとして持つ。

### 4.4 評価（育っているかを数値で見る）

スキルが「編集を再現できるか」を、分析に使っていない保留動画で測る。

| 指標 | 内容 |
|---|---|
| cut_f1 | 素材（ショット列＋音声）から予測したカット点と実際のカット点の一致（±120ms） |
| music_entry_mae_ms | BGM 入りの予測時刻と実際の平均誤差 |
| overlay_iou | テロップ出現区間の重なり |
| asl_err | 予測 ASL と実際の差 |
| human_pref | 2案を並べて人が選ぶ（WorkPilot の A/B と同じ UI） |

バージョンごとにスコアを残し、下がったら前のバージョンに戻せる。

## 5. 画面（UI）

フロント寄りの観点で、最初に必要なのは4画面。

1. **取り込みキュー**: ドラッグ＆ドロップ／フォルダ監視。進捗（分析器ごと）、失敗の再実行、ジャンルタグ付け。
2. **タイムライン・ビューア**: 動画プレイヤーの下に §3 の各トラックを帯で表示。クリックでシーク。
   派生指標（カット密度、ラウドネス、ビート格子）は折れ線で重ねる。**分析結果を自分の目で確認する**ための中心画面。
3. **コーパス**: 動画一覧＋指標の散布図（ASL × カット・オン・ビート率など）。類似ショット検索（埋め込み）。ジャンルごとの分布比較。
4. **スキル工房**: パターン候補の一覧 → 蒸留実行 → diff 承認 → 評価スコアの推移。

UI 技術は Vue 3 + Vite（WorkPilot 本体と同じ。コンポーネントをそのままアドオンへ持ち込める）。タイムライン描画は Canvas（WebGL 不要。帯とポリラインだけ）。
動画再生はブラウザ `<video>` でプロキシ（360p）を再生し、原本は必要時のみ。

## 6. 技術選定（Mac / Apple Silicon 前提）

WorkPilot 本体は **Electron + Vue 3 + Vite、Node のみ（Python なし）、ffmpeg-static 同梱、Swift ヘルパー（apple-stt）同梱** で動いている（§13）。
これに揃えるのが最も摩擦が少ない。Python は DMG に同梱せず、必要なら「任意の外部ヘルパー」に留める。

| 層 | 選定 | 補足 |
|---|---|---|
| アプリ殻 | **Electron + Vue 3 + Vite** | WorkPilot 本体と同一。アドオン化時にそのまま載る |
| Engine | **Node/TypeScript**（CLI + ローカル HTTP/WS） | 外部プロセスを束ねるオーケストレータ。SQLite は better-sqlite3 |
| 動画 I/O | ffmpeg（ffmpeg-static、videotoolbox でHWデコード） | ffprobe-static は arm64 で不備があるため、本体同様に ffmpeg の出力から取得 |
| ショット境界 | ffmpeg `select=gt(scene,T)` + `showinfo` | 無料・高速・Linux でも検証可。ディゾルブは輝度/ヒストグラム連続性で補完。精度が足りなければ TransNetV2（CoreML 変換）を Swift ヘルパーで |
| 無音・黒・静止 | ffmpeg `silencedetect` / `blackdetect` / `freezedetect` | 捨てる区間の検出に直結 |
| ラウドネス | ffmpeg `ebur128` / `astats` | |
| 文字起こし | **Apple Speech**（既存 apple-stt を流用。単語タイムスタンプあり） | 精度が要るときは whisper.cpp バイナリを選択式で |
| OCR | **Apple Vision**（Swift ヘルパー新設） | 無料・高速・日本語可 |
| 音響分類 | **Apple SoundAnalysis**（Swift ヘルパー新設。音楽/発話/拍手/笑い等 300 超のクラス） | BGM 入り・SFX 検出の主力。足りなければ YAMNet を CoreML で |
| ビート/テンポ | aubio CLI（同梱可）または Swift ヘルパー内で実装 | Phase 0 の検証では Python（librosa）を参照実装として使ってよい |
| 埋め込み | CLIP/SigLIP を **CoreML**（Swift ヘルパー）または onnxruntime-node | 類似ショット検索・ゼロショット分類 |
| ベクトル索引 | sqlite-vec（SQLite 拡張）または LanceDB | サーバー不要 |
| 保存 | SQLite + JSON ファイル | WorkPilot の「ただのフォルダ」思想と一致 |
| LLM 接続 | WorkPilot と同じ **@anthropic-ai/claude-agent-sdk / @openai/codex-sdk** | API キー不要を維持。Engine は「LLM プロバイダ」を抽象化 |

**Linux（この開発環境）で検証できるもの / Mac でしか動かないもの**

| Linux で検証可 | Mac 実機のみ |
|---|---|
| ffmpeg 系すべて（ショット、無音、黒、ラウドネス、プロキシ、キーフレーム） | Apple Speech / Vision / SoundAnalysis の Swift ヘルパー |
| Bundle スキーマ、SQLite、ジョブキュー、CLI、パターン抽出、評価スクリプト | CoreML 埋め込み |
| whisper.cpp / onnxruntime（CPU） | videotoolbox HW デコード |

Swift ヘルパー依存の分析器は `platforms: ["darwin"]` を宣言し、Linux では自動スキップされる（Bundle は欠けたトラックを許容する）。

## 7. 非機能要件（大量取り込みに耐える）

- **冪等性**: 同じ動画を二度入れても一度しか分析しない（ハッシュ）。
- **再開性**: 分析器単位のチェックポイント。
- **並列**: CPU 系（ffmpeg、librosa）と GPU/ANE 系（whisper、CLIP）を別ワーカープールに分け、同時実行数を制御。
- **ディスク予算**: cache/ は上限付き LRU。Bundle と knowledge は残し、プロキシは消せる。
- **観測性**: 分析器ごとの所要時間・失敗率を記録。遅い分析器を見つけやすく。
- **スキーマ移行**: `schema` バージョンを持ち、古い Bundle は読み込み時にマイグレーション。

## 8. 権利とプライバシー

- 分析対象が他者の著作物でも、**蓄積するのは派生特徴量（数値・時刻・短いテキスト・埋め込み）** に留め、フレーム画像の長期保存はキーフレーム（低解像度）に限定する。学習データとして再配布しない前提。
- 外部（LLM）へ送るのはキーフレームと数値要約のみ。送る前に件数を提示して承認。
- スキル書き出し時は WorkPilot と同様に、動画のパスや個人情報が混ざっていないか点検する。

## 9A. WorkPilot 側の利用シナリオ: スマホ動画＋テーマ → 完成品

分析アプリで育てたスキルの「使い道」。ユーザー操作は **動画をアップして、テーマを一言頼む** だけにする。

```
ユーザー: スマホ動画 3本 ＋ 「沖縄旅行の Vlog、明るめで」
   │
   ▼
① 素材分析      同じ Engine で素材を Bundle 化（ショット、発話、無音、手ブレ、明るさ、良い瞬間）
② スタイル選択   テーマ → ジャンル/雰囲気 → 該当スキル群を選ぶ（Vlog × 明るい × 旅行）
③ 構成案(LLM)   素材の Bundle ＋ スキル → 「どの素材をどの順で、どこにテロップ・BGM・SFX」を計画
④ 組み立て       recipe.json のルールで計画をタイムラインに展開（カット長、J-cut、BGM入り、ダッキング）
⑤ 素材調達       BGM: Suno / ライセンス済みライブラリ、SFX: 同梱ライブラリ、ナレーション: ElevenLabs
⑥ レンダリング   WorkPilot の既存タイムライン → 書き出し
⑦ 自己評価       完成品を Engine で再分析し、ジャンル指紋・スキルのルールと照合してスコア化
                 低ければ ③ に戻ってやり直し（回数上限あり）
   │
   ▼
ユーザー: プレビューを見て「もう少し静かに」など一言 → ③ から再実行
```

### 9A.1 「汎用的に使える」ための分離

テーマは無限にあるので、スキルを「テーマ別」に作らない。**軸を分けて組み合わせる**。

| 軸 | 例 | スキルの中身 |
|---|---|---|
| ジャンル（構造） | Vlog / ニュース / インタビュー / ドキュメンタリー / ショート | セグメント構成、ASL、フック、チャプターの切り方 |
| 雰囲気（トーン） | 明るい / 落ち着き / 緊張 / エモーショナル | BGM のテンポ・調、カットのリズム、色調、SFX の種類と頻度 |
| 尺・媒体 | YouTube 横長 10分 / ショート 60秒 / SNS 正方形 | 冒頭の密度、テロップサイズ、縦横比ごとの構図 |
| 素材の性質 | 手持ちスマホ / 固定カメラ / 人物中心 / 風景中心 | 手ブレ補正の要否、ジャンプカットの許容、B-roll の使い方 |

「沖縄旅行の Vlog、明るめで」は **Vlog × 明るい × YouTube 横長 × 手持ちスマホ** に分解され、4つの軸のスキルが合成される。
分析アプリ側のパターン抽出も、この4軸でラベル付けして集計する（§4.1 のジャンル集計を4軸に拡張）。

### 9A.2 素材側の分析（撮って出しのスマホ動画に必要なもの）

完成した動画の分析（§1）とは別に、**未編集素材**向けの分析器を追加する。

- **使える瞬間の検出**: 顔がはっきり映る、動きのピーク、笑い声、感嘆の発話、風景が開ける、など「ハイライト候補」をスコア付き区間で出す
- **捨てる区間の検出**: 手ブレ過多、ピンボケ、暗すぎ、無音の長い間、カメラが地面を向く
- **発話の要点**: 文字起こし → この素材で「何を言っているか」を LLM 要約（構成案の材料）
- **連続性**: 同じ場所・同じ人物のショットをまとめる（埋め込みのクラスタ）

これらは Bundle の `tracks.highlights` / `tracks.rejects` として同じ形式に載せる。

### 9A.3 BGM・SFX の扱い（権利を壊さない）

- 学習元の動画から BGM/SFX を**切り出して再利用しない**。学ぶのは「どこで・どんな性質の音を・どの音量で入れるか」という**ルール**だけ。
- 実際の音源は、Suno（WorkPilot 既存連携）での生成、または **ライセンス済みライブラリ**（Epidemic Sound / Artlist 等、またはアプリ同梱の CC0 素材）から、スキルが要求する性質（BPM・調・雰囲気・長さ）で検索して充てる。
- SFX は「whoosh / impact / pop / riser …」の**カテゴリ名で recipe.json に書く**。音源はライブラリ側で解決する。

### 9A.4 品質を上げる仕組み

「ハイクオリティ」を人の感覚任せにせず、3つの数値ループで上げる。

1. **自己評価**（上図 ⑦）: 完成品を再分析し、選んだスキルのルール充足率とジャンル指紋との距離を出す。
2. **ユーザーの手直しを学習**: WorkPilot のタイムラインでユーザーが直した箇所（カット位置、BGM 音量、テロップ）を差分として記録し、分析アプリの「却下/修正データ」に送る。次回の蒸留で反映。
3. **A/B**: 同じ素材で 2 スキルバージョンの完成品を作り、ユーザーが選んだ方を勝ちとして記録（WorkPilot 既存の A/B 機能）。

## 9B. YouTube を学習元にする場合

「YouTube の様々なコンテンツを覚えさせる」は分析アプリの取り込み元の1つとして扱う。

### 9B.1 取り込み設計

- **取り込み元の抽象化**: `Source` を `local_file` / `youtube` / `folder_watch` の実装に分け、どれも同じ Ingest に入る。
- YouTube は **URL・チャンネル・再生リスト**を指定し、メタデータ（タイトル、チャンネル、公開日、再生数、尺、カテゴリ、チャプター）も Bundle に残す。
- **チャンネル単位で「お手本」を登録**できるようにする（例: 旅行 Vlog の好きなチャンネル5つ）。チャンネルごとの指紋がそのまま「この人風」スキルの種になる。
- 再生数・高評価などの指標を持っておくと、「伸びている動画の編集傾向」をパターン抽出の重みに使える。

### 9B.2 保持するもの・しないもの

| 保持する | 保持しない |
|---|---|
| Bundle（時刻付きイベント、数値、短いテキスト） | 動画ファイル本体（分析後に削除。cache は LRU） |
| 低解像度キーフレーム（ショットごとに1枚） | フル解像度フレーム、連続フレーム |
| ショット埋め込み（ベクトル） | 音声波形、BGM/SFX の切り出し |
| 文字起こし（分析目的） | 再配布可能な形のテロップ画像など |

これは**設計上の線引き**であって法的な保証ではない。YouTube の利用規約は公式手段以外でのダウンロードを認めていないため、
取り込み手段（yt-dlp 等）と保持範囲は、実際に運用する前に一度権利面を確認してほしい。
分析アプリの価値は「ルールを学ぶ」ことにあるので、動画本体を持たない設計にしておけば、取り込み手段を後から差し替えても資産は残る。

### 9B.3 大量取り込みの運用

- チャンネル登録 → 新着を定期取り込み（WorkPilot のループと同じ考え方。分析アプリ側にもスケジューラを持つ）
- 1本あたりの分析コストを先に測り（フェーズ0）、1日に何本回せるかを UI に出す
- LLM を使う意味分析は既定オフ。信号分析だけで指紋とパターンは育つ。LLM は「蒸留」のときにまとめて使う

## 10. 進め方（フェーズ）

| フェーズ | ゴール | 中身 |
|---|---|---|
| **0. 検証（2週間）** | パイプラインが成立するか | CLI だけ。ジャンル4種×各5本=20本で Bundle を生成し、タイムライン JSON を目視確認。精度が足りない分析器を特定 |
| **1. MVP** | 1本を取り込み、タイムラインで確認できる | 取り込みキュー＋ビューア。分析器は shots / transitions / speech / music / loudness / ocr の6つ |
| **2. コーパス** | 100本規模で指標比較ができる | 埋め込み・類似検索・散布図。パターン抽出（§4.1）。knowledge/ への Markdown レポート出力 |
| **3. スキル工房** | スキルが1つ、評価付きで育つ | LLM 蒸留 → diff 承認 → evals。まず「ニュース」1ジャンルで通す |
| **4. 高度な分析器** | 編集技術の網羅 | effects / graphics の細分化、J/L-cut、カット・オン・ビート、ダッキング、話者分離 |
| **5. アドオン化** | WorkPilot の動画モードから使える | UI を WorkPilot パネルへ、recipe → タイムライン適用、`wp://` リンク |
| **6. 生成（§9A）** | スマホ動画＋テーマで完成品が出る | 素材分析器、4軸スキル合成、構成案 LLM、BGM/SFX ライブラリ連携、自己評価ループ |
| **7. YouTube 学習（§9B）** | チャンネル登録で勝手に育つ | Source 抽象化、定期取り込み、伸びた動画の重み付け |

フェーズ0で **「分析器の精度」と「LLM の消費量」** の2つを実測してから、フェーズ1以降の分量を決める。

## 11. 主なリスクと手当て

| リスク | 手当て |
|---|---|
| ディゾルブ・ワイプの検出精度が低い | 輝度/ヒストグラム連続性で補完。確信度を Bundle に残し、UI で人が修正できる（修正は学習データに） |
| 音楽と発話の重なりで BGM 入りを誤検出 | 音源分離（Demucs）を「重い分析器」として任意追加 |
| LLM タグ付けでサブスク枠を消費 | 既定はオフ。件数上限と承認。信号分析だけでもスキル蒸留は成立する設計 |
| スキルが抽象的な「感想」になる | 蒸留プロンプトに「数値と根拠（動画ID＋時刻）を必ず付ける」制約。evals で検証できないルールは採用しない |
| Bundle 形式を後から変えたくなる | schema バージョン＋マイグレーション。derived は再計算可能にしておく |
| YouTube 取り込みの規約・権利 | 動画本体を保持しない設計（§9B.2）。取り込み手段は差し替え可能にし、運用前に権利面を確認 |
| 生成物が「それっぽいだけ」で質が低い | 自己評価ループ（§9A.4）。ルール充足率が閾値未満なら再生成。ユーザーの手直しを学習データに |
| テーマが増えるたびにスキルが増殖 | 4軸（ジャンル×雰囲気×媒体×素材）に分解して合成。テーマ別スキルは作らない |

## 13. 実装準備メモ（2026-10-04 時点）

### 13.1 WorkPilot 本体を読んで分かったこと（boice-kazuya/workpilot）

| 項目 | 実態 | 設計への影響 |
|---|---|---|
| アプリ殻 | Electron 42 + Vue 3 + Vite、`electron/main.js` 約 5,000 行の単一ファイル | UI は Vue。アドオンは main.js を肥大化させず、Engine を別プロセスにして IPC を薄く保つ |
| 言語 | Node のみ。Python は使っていない | Engine は Node。Python を DMG に入れない |
| ffmpeg | `ffmpeg-static` 同梱。ffprobe-static は arm64 に x86 バイナリが入る不備があり未使用（ffmpeg のヘッダ出力で代替） | 同じ流儀で ffmpeg のみ使う |
| ネイティブ補助 | `electron/helpers/apple-stt`（Swift、SFSpeechRecognizer、stdout に JSON、TCC 対策で自己再 spawn） | Vision OCR / SoundAnalysis も同じ型のヘルパーとして追加できる |
| スキル | `Vault/WorkPilot/skills/<slug>/SKILL.md` + `.meta.json` + `resources/`、frontmatter は name / description / allowed-tools | 分析アプリの出力 SKILL.md はこの frontmatter を守る。recipe.json と evidence.json は `resources/` に置く |
| タイムライン | `comp.video[]`（kind: clip/image/logo、localPath、in/out、duration）、音声は `auds[]`、fps 基準のフレーム位置で合成 | recipe.json → この comp 形式への変換器を1つ書けば「スキルで切る」が成立する |
| 書き出し | `polish-video`: SFX ミックス（−14dB）、loudnorm（I=−16）、軽い eq/unsharp | ダッキング・BGM 入りの ramp はここを拡張する |
| LLM | `@anthropic-ai/claude-agent-sdk`、`@openai/codex-sdk` | Engine の LLM プロバイダはこの 2 SDK に合わせる |

### 13.2 開発環境（この Linux コンテナ）

- Node 22 / npm / pnpm、Python 3.11 / uv、ffmpeg・ffprobe あり。npm と pip は使える（onnxruntime-node のようにバイナリを後から落とす package は要確認）。
- x86_64 Linux なので Swift ヘルパー・CoreML・videotoolbox は動かない。ffmpeg 系と Engine 本体の検証はここで、Apple 系は Mac 実機で行う。

### 13.3 着手前に残っている決定

1. **コードの置き場所**: 配布専用の `workpilot-releases` には置けない。候補は (a) 新規リポジトリ `videolab`、(b) `workpilot` リポジトリ内の `packages/videolab/`。アドオン化を見据えると (b) が近道だが、分析アプリを独立して育てるなら (a)。
2. **検証用の動画**: Phase 0 に 20 本ほど必要。ユーザー提供か、権利が明確なもの（Big Buck Bunny 等のオープン素材、自分で撮ったスマホ動画）から始める。
3. 既出: 最初のジャンル、LLM 既定、BGM/SFX 供給元、YouTube 取り込み範囲（§12）。
